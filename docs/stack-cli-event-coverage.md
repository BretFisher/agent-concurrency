# gh-stack v0.1.0: API and stacked-event audit

Scope: official `github/gh-stack`, exact commit `a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9`. A fresh detached checkout was verified with `git rev-parse HEAD`. For this audit, I read source and upstream tests. I ran no additional tests or mutating GitHub commands. The pre-existing `work/gh-stack-source` directory had only two files and no Git metadata, so it was not used as version evidence.

## Prune Option 3 scope

The priority is initial stack creation, adding PRs, and restructuring through modify followed by publication. Removal and top-removal edge cases are outside the current priority.

The earlier [TypeScript tests](typescript-stack-prune.md) proved creation and extension through submit. This source audit adds command/API coverage, not new live event-delivery proof. Modify followed by submit is the main remaining event test: the client can unstack and recreate a remote stack from existing PRs. The action should respond if GitHub emits the documented joining events for that recreation; that remains an untested hypothesis.

## What is proved

GitHub's own repository documentation says `pull_request` action `stacked` occurs when a PR is added to a stack. PR creation precedes stack membership; `opened` has no stack object. [Webhook contract](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/docs/src/content/docs/reference/webhooks.md#L6-L12), [stacked contract](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/docs/src/content/docs/reference/webhooks.md#L57-L67).

Client source proves which request a successful code path attempts. It does **not** prove that GitHub emitted an event, delivered a webhook, or started an Actions run. The event expectations below follow the documented contract and require a live event observation to confirm.

`init` creates local stack state; `submit` or `link` creates the GitHub stack. [Command registration](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/root.go#L69-L117).

## Per-command trace

All REST paths below have prefix `/repos/{owner}/{repo}`. GraphQL operations use GitHub's GraphQL endpoint. “PR reads” means GraphQL `FindPRForBranch` / `FindPRByNumber`, with REST stack reads when a remote stack is tracked. [Shared PR refresh](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/utils.go#L464-L475), [Remote refresh](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/utils.go#L676-L735).

## Modify followed by submit

`modify` does not immediately dissolve the remote stack. It records a pending submission only when `s.ID != "" && affectsPRs`; edits restricted to local non-PR branches can avoid that state. [Implementation](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/internal/modify/apply.go#L650-L667).

On the next `submit`, `handlePendingModify` resolves the previous stack number, calls Unstack, then clears local `s.ID` and `s.Number`. This happens **before** the per-branch push and PR-base updates. `syncStack` then creates a new remote stack if no matching stack remains. Existing PR numbers are reused when their branches still have PRs; a renamed branch can need a new PR. The expected `stacked` action is a new membership event on the new stack, even for a previously stacked PR number. This last statement is a contract-based inference, not an observed delivery. [Recreation implementation](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L623-L681), [Execution order](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L174-L246), [Create result stores new ID/number](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L890-L899).

The word “delete” in CLI output/comments does not mean HTTP DELETE. The implementation is POST unstack. A 204 means dissolved; a 200 means some PRs remain. Also, pending-modify handling ignores the returned `dissolved` boolean, so do not claim every unstack request necessarily destroys the old stack. [Caller](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L654-L679), [HTTP/result handling](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/internal/github/github.go#L570-L590).

## Limits and version traps

- At this commit, sync calls `syncStack` (`sync.go:298`). There is no `syncStackWithRemoteAdditive` symbol. The actual update implementation is still additive.
- The comment above `syncStack` incorrectly describes PUT/full-list replacement. Follow the executable code: GetStack → equality/appendDelta → POST add delta. [Stale comment](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L694-L704), [Actual code](https://github.com/github/gh-stack/blob/a1b4a3d4d0bcde9ec3a78ab99b2d63af121857a9/cmd/submit.go#L820-L853).
- To prove event delivery, run an explicitly authorized live test and capture a payload with `action: stacked`, PR number, stack ID/number, and delivery/run evidence. Client unit tests and an API success response cannot settle event fan-out or delivery timing.

## Live tests still needed (not run)

1. Initial creation: `init` two branches, then `submit --auto`; confirm no join event before submit, then record each PR's `stacked` payload and returned stack number.
2. Addition: `add` one branch to that stack, commit, then `submit --auto`; confirm only the new PR is supplied to POST add, record its join payload, and check whether existing members receive any event. Repeat an unchanged submit to check for no membership event.
3. Reorder: run interactive `modify` to reorder PR branches; confirm remote grouping has not yet changed. Then submit; capture POST unstack, branch pushes/base updates, POST create, new stack number, and `stacked` payloads for reused PR numbers. This verifies the contract-based recreation expectation.

For every test, record API response, `X-GitHub-Delivery` where available, payload action/PR/stack identity, and the resulting Actions run. These are proposed tests only; no authorization for mutation is implied.
